# Graph RAG — Scoping (2026-05-24)

## Pain

Projects are perceived purely textually in this pipeline — via file names, decision-record MDs, DOCS.md tables, ticket descriptions. There is no visual node view showing how modules connect, which decisions touch which code areas, which historical topics reference which src/ files, which sources feed into which pipeline steps. For disorientation moments in larger projects this is a real friction point — the user says: "I never see the project visually in front of me".

## Two Possible Meanings of "Graph RAG"

Before any further discussion, the direction needs disambiguating:

**Direction A: Project visualization as a graph.** Code-symbol graph (functions, classes, modules with import edges), decisions graph (which decision record references which source files, which historical topics led to which recommendation), source-inventory graph (which sources are cited in which decisions). Tool-wise: extract via AST/ripgrep, render as an interactive graph (Pyvis / D3 / Obsidian-style backlinks / Mermaid). Output: a navigable map of the project. Retrieval might be an add-on here, but the primary goal is visualization.

**Direction B: Graph-augmented retrieval.** Classic GraphRAG paradigm (Microsoft GraphRAG, LightRAG, etc.): entities + relations are extracted from the corpus and stored as a knowledge graph. At retrieval time, the KG is searched alongside chunk-based search — an entity match leads to connected entities, multi-hop reasoning becomes possible. Output: better answers to questions that must combine multiple sources ("which decisions relate to topic X AND which of those decisions reference source Y"). Visualization is possible here but not the goal.

Both are combinable — Direction A directly solves the orientation pain, Direction B would improve our searches ad-hoc but is a substantially bigger implementation effort.

## Initial Indication

The user pain is "I never see the project visually" — that clearly favors Direction A as the first lever. Direction B could be layered on later.

## Direction A Mechanics (Sketch)

- **Extract sources:** Python AST for the src/ symbol graph (functions, classes, imports), Markdown parser for decision records + DOCS.md (extracts file-path references, historical-topic links, source-inventory pointers), git log for commit→file mapping
- **Node types:** module, function, decision record, historical topic, source (external), ticket
- **Edge types:** imports, calls, references, supersedes, references-source, decision-touches-module, topic-led-to-decision
- **Storage:** graph as JSON (or Neo4j if we want a DB anyway, or NetworkX in-memory for read-only snapshots)
- **Rendering:** static (Mermaid for doc embedding) OR interactive (Pyvis HTML, rendered once, browser-navigable)

Worth checking skeptically: does the tool-build effort pay off against a simple hand-maintained Markdown index? Yes for growing projects, likely overkill for small ones — gut feeling is that a list suffices at three modules with 10 functions each; at 30 modules with cross-referenced decisions the graph becomes critical.

## What a Probe Step Would Look Like

`dev/graph_rag/probe_direction_a.py`: a script that runs against `RAG/`, extracts AST + Markdown, renders a Pyvis HTML. Look at the output, judge whether it really addresses the pain. If yes → a follow-up discussion on hosting (local HTML, live server, Obsidian vault as the display surface). If no → try another direction or drop the idea.

## Open Questions

- Which direction to prioritize? Proposal: Direction A (visualization); Direction B only after eval stabilization, if at all.
- Which project first? RAG itself is small (~10 src/ modules) — testing on RAG is low-effort but may show too little of the pain. Monitor_CC is bigger (~30 src/ modules + many historical topics) — more representative but more setup.
- Where to host? Static HTML in the repo (committed, opened on click)? A small dedicated server? Obsidian vault as a view layer? User preference unknown.
- GitHub research hasn't happened yet: what tools already exist (mermaid-cli, pyvis, networkx, py2neo, GraphRAG frameworks like Microsoft GraphRAG / LightRAG / nano-graphrag), what do others with similar pain do.
